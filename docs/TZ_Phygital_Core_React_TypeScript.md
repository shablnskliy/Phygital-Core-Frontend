# Техническое задание на разработку сайта Phygital Core

**Редакция:** 5.0  
**Основание:** исходное ТЗ 4.0 и предоставленные дизайн-макеты  
**Статус:** документ для оценки, проектирования, разработки и приёмки MVP

---

## 1. Общие сведения

### 1.1. Назначение системы

Phygital Core — веб-платформа для фиджитал-турниров. Система должна включать:

- публичный сайт;
- регистрацию и авторизацию;
- личный кабинет пользователя;
- личный кабинет администратора;
- работу с командами и заявками на создание команд;
- работу с турнирами и заявками команд на участие;
- административную панель;
- журнал административных действий.

Основная бизнес-логика и данные находятся на backend. Клиентское приложение не является источником истины для ролей, прав, статусов и связей сущностей.

### 1.2. Язык и часовой пояс

- основной язык интерфейса — русский;
- даты отображаются в формате `ДД.ММ.ГГГГ`;
- время отображается в формате `ЧЧ:ММ`;
- часовой пояс по умолчанию — `Asia/Yekaterinburg`;
- даты в API передаются в ISO 8601.

### 1.3. Обязательный технологический стек

#### Frontend

- React 18 или новее;
- TypeScript 5 или новее в строгом режиме (`strict: true`);
- Vite;
- React Router;
- TanStack Query для серверного состояния;
- React Hook Form + Zod для форм и валидации;
- CSS Modules или SCSS Modules;
- библиотека иконок с единым визуальным стилем;
- графики — Recharts либо эквивалентная React-библиотека.

Использование `any` допускается только с обоснованием. Компоненты, props, ответы API, формы и состояния должны быть типизированы.

#### Backend

Рекомендуемый стек, обеспечивающий единый TypeScript-контур:

- Node.js LTS;
- TypeScript;
- NestJS либо Express/Fastify с модульной архитектурой;
- PostgreSQL;
- Prisma ORM либо эквивалент;
- OpenAPI 3.0 для документации API.

Допустима замена backend-технологий по согласованию, но React и TypeScript на frontend обязательны.

### 1.4. Архитектура frontend

Рекомендуемая структура:

```text
src/
├── app/             # конфигурация приложения, роутер, провайдеры
├── pages/           # страницы маршрутов
├── widgets/         # крупные блоки: header, footer, admin sidebar
├── features/        # авторизация, формы заявок, редактирование
├── entities/        # user, team, tournament, application
├── shared/
│   ├── api/
│   ├── ui/
│   ├── lib/
│   ├── hooks/
│   ├── assets/
│   ├── styles/
│   └── types/
└── main.tsx
```

Необходимо разделять UI, работу с API, бизнес-логику и типы. Общие компоненты не должны дублироваться между публичной частью, личным кабинетом и админ-панелью.

## 2. Источники требований и приоритеты

При реализации использовать следующий приоритет:

1. настоящее ТЗ;
2. предоставленные дизайн-макеты;
3. согласованные изменения заказчика;
4. исходное ТЗ 4.0.

Макеты задают визуальный стиль, композицию и основные состояния интерфейса. Тексты и демонстрационные данные на макетах не должны жёстко встраиваться во frontend, если в этом ТЗ они обозначены как динамические.

### 2.1. Нормализованные расхождения макетов

- основное меню: «Главная», «Турниры», «Команды», «Правила», «FAQ», «Контакты»;
- раздела «Новости» в MVP нет;
- регистрация выполняется без телефона: телефон заполняется позднее в профиле;
- смена пароля требует текущий пароль, новый пароль и подтверждение;
- кнопка «Страница турнира» ведёт на реальную страницу `/tournaments/:id`;
- «Настройки» в админ-панели не входят в MVP: пункт скрывается до появления отдельного ТЗ;
- контактные данные должны храниться в единой конфигурации, чтобы не расходиться между страницами и footer;
- в FAQ шестая строка «Остались вопросы?» открывает форму вопроса и не раскрывает статический ответ.

## 3. Роли и права

### 3.1. Гость

Может:

- просматривать публичные страницы;
- открывать вход и регистрацию;
- просматривать команды и составы;
- просматривать турниры;
- отправлять вопрос через FAQ.

Не может:

- отправлять заявки на создание команды;
- подавать команду на турнир;
- открывать личный кабинет и `/admin`.

При попытке защищённого действия открывается вход. После успешного входа пользователь возвращается к исходному сценарию.

### 3.2. Пользователь

Может:

- выполнять все действия гостя;
- редактировать разрешённые данные профиля;
- менять пароль;
- видеть свои команды;
- подавать заявку на создание команды;
- подавать заявку существующей команды на турнир, если является её капитаном.

### 3.3. Администратор

Может:

- редактировать свой профиль и менять пароль;
- открывать административную панель;
- управлять пользователями, командами, турнирами и заявками;
- просматривать статистику и логи.

Администратор не является участником или капитаном команды и не подаёт игровые заявки.

Права проверяются сервером при каждом защищённом запросе. Скрытие элементов на frontend не является механизмом авторизации.

## 5. Общий визуальный стиль

Интерфейс должен соответствовать макетам:

- тёмная фиолетово-чёрная база;
- пурпурные, фиолетовые и голубые акценты;
- светящиеся границы, мягкие тени и градиенты;
- крупная контрастная типографика;
- стеклянные полупрозрачные панели;
- декоративные диагонали, сетки и геометрические элементы;
- изображения спортивно-технологической тематики;
- скругления элементов и заметные состояния наведения/фокуса.

Декоративная графика не должна ухудшать читаемость, доступность, скорость загрузки или перекрывать интерактивные элементы.

### 5.1. Дизайн-токены

Цвета, градиенты, радиусы, тени, отступы, размеры шрифтов и уровни `z-index` оформляются как единые токены. Запрещено хаотичное дублирование значений по компонентам.

### 5.2. Общие компоненты

- `Header`;
- `Footer`;
- `PageHero`;
- `Button`, `IconButton`;
- `Input`, `PasswordInput`, `Textarea`, `Select`, `DatePicker`, `Checkbox`;
- `Modal`, `Drawer`, `ConfirmDialog`;
- `Tabs`, `Accordion`, `Dropdown`;
- `Card`, `Badge`, `Table`, `Pagination`;
- `Toast`, `Alert`, `Skeleton`, `EmptyState`, `ErrorState`;
- `FileUpload`;
- `ProtectedRoute`, `AdminRoute`.

## 8. Турниры

### 8.1. Список турниров

**Маршрут:** `/tournaments`

Карточка турнира содержит:

- изображение;
- публичный номер;
- название;
- дисциплину;
- статус;
- даты;
- город;
- краткое описание;
- кнопку «Страница турнира»;
- кнопку «Зарегистрировать команду» для доступного к регистрации турнира.

Список сортируется по дате: сначала ближайшие предстоящие, затем текущие, затем завершённые.

### 8.2. Статус турнира

Статус вычисляется сервером:

```text
startAt > now                       -> UPCOMING
startAt <= now и endAt >= now      -> ACTIVE
endAt < now                         -> COMPLETED
```

В интерфейсе: «Предстоящий», «Идёт», «Завершён». Администратор не задаёт статус вручную.

### 8.3. Страница турнира

**Маршрут:** `/tournaments/:id`

Содержит:

- изображение и название;
- описание;
- дисциплину и формат;
- даты, город и площадку;
- правила/регламент конкретного турнира;
- статус;
- состояние регистрации;
- кнопку подачи заявки, если это разрешено.

Если турнир не найден — 404. Для завершённого турнира форма заявки недоступна.

### 8.4. Заявка на турнир

Форма открывается в модальном окне. Заявка всегда связывает существующие `Team` и `Tournament`.

Условия:

- пользователь авторизован;
- пользователь является капитаном выбранной команды;
- команда ещё не подавала заявку на этот турнир;
- турнир принимает заявки.

Поля:

- команда — обязательный выбор из команд, где пользователь капитан;
- капитан — заполняется автоматически и недоступен для изменения;
- дополнительная информация — необязательно, до 500 символов.

После отправки показывается подтверждение. Повторная отправка той же команды на тот же турнир запрещена сервером.

## 9. Команды

**Маршрут:** `/teams`

### 9.1. Список

Отображается список команд с логотипом, названием и дисциплиной. Нажатие открывает боковую панель или блок состава:

- название;
- участники;
- капитан с отдельным бейджем.

### 9.2. Заявка на создание команды

Кнопка «Создать команду» доступна авторизованному пользователю и открывает модальное окно.

Поля согласно макету:

- название команды — обязательное, 2–50 символов;
- имя и фамилия капитана — обязательное;
- состав участников — обязательное текстовое поле, до 500 символов.

Все указанные участники должны иметь зарегистрированные аккаунты. Администратор вручную сопоставляет их с пользователями при обработке заявки.

`TeamApplication` не является `Team`. Одобрение заявки не создаёт команду автоматически.

```text
Пользователь -> TeamApplication -> проверка администратором
-> ручное создание Team -> добавление TeamMember -> назначение капитана
```

После отправки пользователь видит сообщение «Заявка отправлена. Организатор свяжется с вами для подтверждения».

## 11. FAQ и форма вопроса

**Маршрут:** `/faq`

### 11.1. Аккордеон

Пять статических вопросов:

1. Где проходят мероприятия?
2. Что нужно для участия?
3. Как создать команду?
4. Как принять участие в турнире?
5. Как определяется победитель?

По умолчанию все закрыты. Одновременно открыт максимум один ответ. Строка «Остались вопросы?» открывает форму вопроса.

### 11.2. Форма «Задать вопрос»

Поля:

- имя — обязательное, 2–100 символов;
- email — обязательный и валидный;
- тема — обязательный выбор;
- вопрос — обязательный, 10–500 символов согласно макету.

Темы: участие в турнире, регистрация команды, правила, сотрудничество, технический вопрос, другое.

После отправки:

- вопрос сохраняется или отправляется на согласованный адрес организатора;
- пользователь видит успешное состояние;
- повторная отправка во время запроса блокируется.

Необходимо предусмотреть защиту от спама: rate limit и скрытое honeypot-поле либо CAPTCHA по согласованию.

## 13. Авторизация и регистрация

### 13.1. Общие требования к модальным окнам

- затемнение и размытие фона;
- закрытие крестиком и клавишей `Esc`;
- закрытие по клику на backdrop только при отсутствии несохранённых данных;
- удержание фокуса внутри окна;
- возврат фокуса инициировавшему элементу;
- блокировка прокрутки страницы;
- понятные состояния loading/error/success.

### 13.2. Вход

Поля:

- email;
- пароль;
- чекбокс «Запомнить меня».

Пароль можно показать/скрыть. Ссылка «Забыли пароль?» открывает окно с инструкцией обратиться к администратору и актуальными контактами.

Ошибки авторизации не должны раскрывать существование конкретного email. Пользователю возвращается единое сообщение: «Неверный email или пароль».

### 13.3. Регистрация

Поля согласно утверждённому макету:

- email;
- имя;
- фамилия;
- пароль;
- подтверждение пароля;
- согласие с политикой конфиденциальности.

Телефон не является полем регистрации и заполняется в профиле.

Требования:

- email уникальный;
- имя и фамилия — 2–50 символов;
- пароль — минимум 8 символов, минимум одна буква и одна цифра;
- подтверждение совпадает;
- согласие обязательно.

После успешной регистрации показывается предложение войти. Автоматический вход допустим только после отдельного согласования.

### 13.4. Сессия

Предпочтительно использовать защищённую серверную сессию или access/refresh token схему с refresh token в `HttpOnly`, `Secure`, `SameSite` cookie. Не хранить долгоживущие токены в `localStorage`.

## 14. Личный кабинет

**Маршрут:** `/profile`

Содержит вкладки «Профиль» и «Безопасность».

### 14.1. Профиль пользователя

Отображаются:

- имя и фамилия;
- email;
- телефон;
- дата рождения;
- Telegram;
- список «Мои команды».

Редактируются телефон, дата рождения и Telegram. Имя, фамилия и email обычный пользователь не меняет.

Команда в списке показывает название и роль пользователя; переход открывает состав. При отсутствии команд показывается empty state.

### 14.2. Профиль администратора

Дополнительно отображаются бейдж «Администратор» и кнопка «Админ-панель». Администратор может редактировать имя, фамилию, email, телефон, дату рождения и Telegram.

### 14.3. Безопасность

Поля:

- текущий пароль;
- новый пароль;
- подтверждение нового пароля.

Все поля обязательны. Новый пароль должен отвечать требованиям и отличаться от текущего. После успешной смены остальные активные сессии аннулируются, кроме текущей, либо все сессии — по выбранной политике проекта.

### 14.4. Выход

Выход завершает серверную сессию, очищает клиентский кэш персональных данных и перенаправляет на главную.

## 15. Административная панель

**Базовый маршрут:** `/admin`

Desktop-компоновка: верхняя панель, постоянный левый sidebar и рабочая область. На планшете sidebar сворачивается, на мобильном становится выезжающим меню.

Разделы:

- статистика;
- пользователи;
- команды;
- заявки на создание команд как вкладка раздела команд;
- турниры;
- заявки на турниры;
- логи;
- «Вернуться на сайт».

### 15.1. Статистика

Карточки:

- пользователи;
- команды;
- турниры;
- заявки.

Показываются итоговое значение и изменение за 30 дней. Для турниров — количество активных.

График поддерживает периоды: 7 дней, 30 дней, 3 месяца, 6 месяцев, год. Серии: новые пользователи, команды, заявки, регистрации на турниры.

Также отображаются последние административные действия и быстрые действия.

### 15.2. Пользователи

Возможности:

- поиск по имени, фамилии и email;
- фильтр по роли;
- серверная пагинация;
- просмотр карточки;
- редактирование разрешённых данных;
- смена роли;
- принудительный сброс пароля;
- удаление/деактивация с подтверждением.

Таблица: пользователь, email, телефон, Telegram, количество команд, роль, дата регистрации, действия.

Последнего активного администратора нельзя понизить в роли или удалить.

### 15.3. Команды

Две вкладки:

- «Команды»;
- «Заявки на создание команды».

Для команд доступны поиск, фильтр по дате, пагинация, просмотр и редактирование.

Карточка команды содержит дату создания, капитана и состав. Действия:

- изменить название;
- назначить капитана из состава;
- добавить зарегистрированного пользователя;
- удалить участника;
- удалить/архивировать команду.

Нельзя назначить капитаном пользователя вне состава. Одновременно у команды ровно один капитан.

### 15.4. Создание команды администратором

Форма:

1. название команды;
2. добавление зарегистрированных пользователей;
3. выбор одного капитана из добавленного состава.

Проверяется уникальность названия без учёта регистра. Администратор не может добавить себя. Создание команды не создаёт `TeamApplication`.

### 15.5. Заявки на создание команд

Таблица: тип, название команды, капитан, состав, дата, статус, действие просмотра.

Статусы: `NEW`, `APPROVED`, `REJECTED`.

В карточке доступны «Одобрить» и «Отклонить». Одобрение меняет статус заявки, но не создаёт команду автоматически. После одобрения администратор создаёт команду отдельной формой.

Повторная обработка уже завершённой заявки запрещена без отдельного действия возврата в работу.

### 15.6. Турниры

Возможности:

- поиск;
- фильтр по городу и датам;
- пагинация;
- просмотр;
- создание;
- редактирование;
- удаление/архивация с подтверждением.

Поля турнира:

- название;
- краткое описание до 500 символов;
- полное описание;
- дисциплина;
- формат;
- город;
- площадка;
- изображение;
- дата и время начала;
- дата и время окончания;
- дата окончания приёма заявок;
- регламент.

Изображение: JPG, PNG или WebP, до 5 МБ. Проверяется MIME type и фактический формат файла. Дата окончания должна быть позже даты начала.

### 15.7. Заявки на турниры

Таблица: тип, команда, капитан, турнир, дата, статус, просмотр.

Карточка содержит команду, капитана, турнир, состав, дополнительную информацию и дату подачи. Действия: «Одобрить» и «Отклонить».

Одобрение не меняет статус турнира и не создаёт команду.

### 15.8. Логи

Фильтры:

- период;
- тип действия;
- тип объекта;
- поиск по деталям.

Таблица: дата/время, администратор, действие, объект, ID объекта, детали.

Логируются создание, изменение, удаление/архивация, смена роли, сброс пароля, создание/изменение команды и турнира, обработка заявок. Логи доступны только для чтения и не удаляются через UI.

## 18. Валидация

- email нормализуется и проверяется на frontend и backend;
- телефон хранится в нормализованном виде и отображается по маске;
- Telegram допускает `@username` или `username`, в БД хранится без `@`;
- текстовые поля очищаются и ограничиваются по длине;
- даты проверяются на логическую последовательность;
- файл проверяется по размеру, MIME type и сигнатуре;
- все идентификаторы и права проверяются на backend;
- кнопки отправки блокируются до завершения запроса;
- сервер защищён от повторных конкурентных операций.

Ошибки показываются рядом с полями, а общая ошибка — в верхней части формы или toast. Введённые пользователем данные не теряются при исправимой ошибке.

## 19. Состояния интерфейса

Для всех данных и действий обязательны:

- `loading` — skeleton/спиннер без скачков макета;
- `empty` — понятный текст и уместное действие;
- `error` — объяснение и повтор запроса;
- `success` — toast или встроенное успешное состояние;
- `disabled` — визуально и программно недоступное действие;
- `confirm` — подтверждение опасной операции.

Текст удаления: «Удалить объект? Это действие нельзя отменить». Если применяется архивирование/деактивация, текст должен точно описывать фактическое действие.

## 20. Адаптивность и доступность

### 20.1. Контрольные ширины

- desktop: от 1280 px;
- tablet: 768–1279 px;
- mobile: 360–767 px.

Верстка должна корректно работать и между контрольными ширинами. На мобильных:

- формы одноколоночные;
- модальные окна занимают почти всю ширину и не выходят за viewport;
- таблицы превращаются в карточки либо имеют контролируемый горизонтальный скролл;
- админ-sidebar становится drawer;
- декоративные изображения упрощаются или скрываются без потери содержания.

### 20.2. Доступность

- семантическая HTML-разметка;
- управление с клавиатуры;
- видимый `focus-visible`;
- `aria-label` для иконок;
- `aria-expanded` у аккордеонов и меню;
- связка label и поля;
- ошибки доступны screen reader;
- контраст не ниже WCAG 2.1 AA для основного текста и элементов управления;
- `prefers-reduced-motion` отключает необязательные анимации.

## 21. Безопасность

- пароли хешируются Argon2id или bcrypt с актуальными параметрами;
- HTTPS обязателен в production;
- защита от XSS, CSRF, SQL injection и mass assignment;
- CORS ограничен доверенными origin;
- rate limit для входа, регистрации и публичной формы;
- security headers, включая CSP;
- cookies имеют `HttpOnly`, `Secure`, `SameSite`;
- административные маршруты и методы защищены RBAC;
- чувствительные данные не попадают в логи;
- загрузки файлов имеют whitelist форматов и случайные имена;
- секреты хранятся в переменных окружения;
- сообщения входа не позволяют перечислять зарегистрированные email.

## 26. Критерии приёмки

Система принимается, если:

- интерфейс визуально соответствует предоставленным макетам и настоящему ТЗ;
- frontend реализован на React и TypeScript без ошибок типизации;
- все заявленные маршруты и состояния работают;
- гость не выполняет защищённые действия;
- пользователь не получает доступ к административным API и UI;
- регистрация, вход, выход и сессия работают корректно;
- пользователь редактирует только разрешённые данные;
- смена пароля проверяет текущий пароль;
- список команд пользователя формируется по данным БД;
- `TeamApplication` не создаёт `Team` автоматически;
- администратор создаёт команду из зарегистрированных пользователей и назначает капитана из состава;
- `TournamentApplication` связывает существующие Team и Tournament;
- одну команду нельзя дважды заявить на один турнир;
- статусы турниров вычисляются автоматически;
- ближайший турнир выбирается сервером;
- администратор управляет пользователями, командами, турнирами и заявками;
- опасные действия требуют подтверждения;
- административные действия записываются в неизменяемый через UI журнал;
- loading, empty, error и success реализованы для всех асинхронных экранов;
- формы имеют клиентскую и серверную валидацию;
- адаптивность проверена от 360 px;
- критические сценарии покрыты e2e-тестами;
- проект запускается по README и проходит build, typecheck, lint и test.

## 27. Вопросы, требующие подтверждения до production

Следующие значения не должны определяться разработчиком произвольно:

- окончательные телефон, email, адрес, режим работы и ссылки на соцсети;
- ссылка на политику конфиденциальности и её утверждённый текст;
- домен и параметры production-развёртывания;
- допустимое количество участников команды для каждой дисциплины;
- правила приёма заявок и крайний срок регистрации;
- удаление или архивирование связанных пользователей, команд и турниров;
- способ доставки вопросов из FAQ организаторам;
- финальные логотипы, шрифты и права на графические ассеты.

До подтверждения используются централизованные тестовые значения, явно помеченные как демонстрационные.
